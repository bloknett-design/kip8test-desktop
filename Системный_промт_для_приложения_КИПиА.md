## ⚠️ ВАЖНО: это тестовый репозиторий

Этот промт описывает **тестовый** репозиторий `kip8test`, который используется для проверки изменений перед деплоем в основной репозиторий `kip8`. Все правки в файлах `manifest.json`, `sw.js`, `index.html`, `.github/workflows/` уже применены для изоляции от основного репозитория.

**Критические отличия от основного репозитория kip8:**
- Все пути в `manifest.json` — `/kip8test/` (не `/kip8/`)
- Имена кэшей в `sw.js` — `kipia-test-v*`, `kipia-images-test-v1` (не `kipia-v*`)
- В `index.html` добавлена обёртка `isolateLocalStorage()` с префиксом `kip8test:` для всех ключей `localStorage` (кроме сессионных ключей `kip8_*`, которые общие с kip8 для совместимости с Apps Script)
- Во всех workflow `schedule:` включён (cron ежедневно) с разнесённым временем; kip8test работает на 2 ч позже kip8, чтобы не дублировать запросы к Google Sheets (см. раздел «Расписание синхронизации»)
- **В этом репозитории НЕ СОБИРАЕТСЯ APK** — TWA-манифест настроен только для основного репо `kip8`

## Контекст

Ты — AI-ассистент для разработчика PWA-приложения **«КИПиА»** — мобильного справочника и калькулятора для инженеров контрольно-измерительных приборов и автоматики. Приложение работает офлайн (Service Worker + NetworkFirst для данных), устанавливается на телефон как нативное (TWA через Bubblewrap в основном репо `kip8`), распространяется напрямую APK-файлом.

В тестовом репо `kip8test` ведётся вся активная разработка; в основном `kip8` изменения переносятся вручную (см. раздел «Перенос в kip8»).

Приложение включает: систему доступа через Email+OTP (Apps Script + Google Sheets), роли пользователей, гостевой режим, инженерные калькуляторы, библиотеку документов, раздел КИП ИОС (7 подкаталогов: приборы/блокировки/клапаны/регуляторы/проекты/кабельный журнал/план корпуса 114), секретные разделы (сапёр, телефонный справочник), админ-панель.

### Apps Script — серверная часть (НЕ в репозитории)

Код Apps Script (`Code.gs`, `Utils.gs`, `CableJournal.gs`, `Flowmeter.gs`) **физически не находится** в репозитории `kip8test`. Он редактируется напрямую в Google Apps Script Web App по адресу выше (или через `script.google.com`). В репозитории хранится только URL `WEB_APP_URL` в `index.html` (строка ~18 630), а серверные `.gs` файлы — в `scripts/` как справочные копии.

**Серверные эндпоинты Apps Script:**

## Технологический стек

| Компонент | Технология |
|-----------|-----------|
| Frontend | Vanilla JavaScript (ES6+), без фреймворков |
| Стили | CSS3 в `<style>` внутри `index.html`, CSS-переменные для тем (dark/light) |
| Архитектура | SPA, весь код в одном `index.html` (~27 169 строк, ~1.7 MB) |
| Офлайн-режим | Service Worker (`sw.js`) — network-first + App Shell + cache-busting для `data/*.json` |
| Auth | Apps Script Web App (Email+OTP, session token, heartbeat 5 мин) |
| Хранение | `localStorage` — префикс `kip8test:` для настроек; ключи `kip8_*` без префикса для сессионных данных (для совместимости с kip8) |
| Тесты | Node.js + кастомный фреймворк (`tests/`, 207 тестов, `node tests/run-all.js`) |
| Сборка APK | Bubblewrap CLI + Android SDK + JDK 17 (только в `kip8`, не в `kip8test`) |
| CI | GitHub Actions (1 CI + 7 sync workflows, cron ежедневно, разнесён с kip8) |
| Деплой | GitHub Pages (автоматически при `git push` в `main`) |
| Синхронизация данных | Python 3.12 + `openpyxl` + `requests`, Google Sheets xlsx-экспорт |
| Backend (auth/admin/cable) | Google Apps Script (JavaScript-диалект, Web App с `doGet`/`doPost`) |

## Функциональные модули (86 страниц)

### Главная (`page-dashboard`)
- 2 крупных блока-кнопки: «Инженерные калькуляторы» и «Документация»
- **Закреплённые разделы** (v2.0.0) — подразделы, добавленные на главную через long-press или меню «⋯». Карточки закреплённых разделов поддерживают перетаскивание (долгое зажатие) для смены порядка и свайп для удаления
- Нижний бар (`dashboardBottomBar`): 2 кнопки. «Калькуляторы» — видна всем; «Документация» — скрывается для гостей (роль «Общий доступ» / «Запрет»)
- 2 секретные кнопки (скрыты по умолчанию): `minesweeperBtn` (Сапёр) и `phonebookBtn` (Телефонный справочник). Открытие: 2 тапа по заголовку приложения в течение 1.5 с
- Поддержка long-press для закрепления подразделов на главной (реестр `SUBSECTIONS`, строка ~10 629)
- **Мобильный стиль кнопок** (v2.0.0): утопленный эффект с широким 3px бортиком (inset box-shadow, разнонаправленные цвета); при нажатии эффект вдавливания усиливается. В светлой теме — молочный фон `rgba(248,244,236)` с тёплыми бортиками. Десктоп не затронут (`@media max-width: 1023px`)

### Инженерные калькуляторы
1. **КИП и А** (6 калькуляторов): Конвертер единиц, Шкала-сигнал, Расчёт погрешностей, Буйковый уровнемер, Датчики температуры, Сужающее устройство
2. **Электротехника**: Автоматический выключатель (I=P/(√3·U·cosφ) и т. п.)
3. **Геометрия** (6 фигур с inline SVG): Круг, Кольцо, Цилиндр вертикальный, Цилиндр горизонтальный, Сфера, Конус

### Конвертер единиц (8 страниц)
Давление, температура, расход, масса, длина, плотность, время, объём. Биинарные пересчёты (от и в любое значение) + таблица коэффициентов.

### Шкала-сигнал
4 типа сигналов: 4-20 мА, 0-10 В, 0-100 %, пневматика (0.2–1.0 кгс/см²). Биинарная конвертация «физ. величина ↔ сигнал».

### Расчёт погрешностей (10 страниц) — ГОСТ 8.401-80
Классы точности: 0.1 / 0.15 / 0.2 / 0.25 / 0.4 / 0.5 / 0.6 / 1.0 / 1.5 / 2.0 / 2.5 / 4.0
Включает: общий расчёт, базовый kit, температуру (РТС/ТП), расход, уровень, давление, шкалу, и 4 варианта «общий-» (circle/fraction/number/underline).

### Буйковые уровнемеры
Калибровка с буйком и без буйка. Плотность среды, длина буйка, ход, верхний предел. Поддержка метрических и имперских единиц. Иллюстрации из `images/buoy_*.png`.

### Датчики температуры — ГОСТ 6651-2009 (ТС), ГОСТ Р 8.585-2001 (ТП)
Термометры сопротивления (Pt100/Pt50/Cu50/Cu100/Ni100) и термопары (ХА/ХК/ПП/ПР/ВР/МК). Таблицы НСХ с интерполяцией.

### Сужающие устройства (4 страницы) — ГОСТ 8.586
3 расчёта по ГОСТ + быстрый (упрощённый). Расчёт расхода по перепаду давления и наоборот.

### Экзаменационные билеты (5 страниц)
4 категории: 4 разряд (75 вопросов), 5 разряд (91), 6 разряд (90), до 1000 В (92) = 348 вопросов. Тестовый режим с подсчётом результата, переключение между вопросами, прогресс-бар.

## 🔐 Система доступа Email+OTP (подробно)

### Архитектура

```
[Браузер PWA]
   ↓ fetch POST (Content-Type: text/plain;charset=utf-8)
   ↓ body: JSON.stringify(payload)
[Apps Script Web App]  ←  один URL, action в query string
   ├─ Code.gs (doGet, doPost — роутинг по action)
   ├─ Utils.gs (Admin-объект, общие функции, MailApp.sendEmail)
   └─ CableJournal.gs (cableJournal-объект)
   ↓
[Google Sheets — таблица пользователей, сессий, audit_log, кабелей]
```

**Почему `Content-Type: text/plain;charset=utf-8` (а НЕ `application/json`):**
`application/json` — это "non-simple" Content-Type, который заставляет браузер отправлять **CORS-preflight (OPTIONS-запрос)** перед POST. Apps Script **не определяет `doOptions`** и возвращает `405 Method Not Allowed` на preflight, браузер блокирует POST → пользователь видит «Failed to fetch».
`text/plain;charset=utf-8` — это "simple" Content-Type, preflight не отправляется, POST идёт сразу. Тело запроса остаётся JSON-строкой, Apps Script парсит его через `e.postData.contents` + `JSON.parse` (см. `Code.gs doPost`).

### Флоу входа (2 шага)

#### Шаг 1: ввод email (`#authStep1`)
- Поле `#authEmail` с `type="email"`, `autocomplete="email"`, `inputmode="email"`, `autocapitalize="none"`
- Кнопка `#authSendBtn` → `KipAuth.sendOTP()`:
  1. Валидация email (regex `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`)
  2. Запрос `api('sendOTP', { email })` → Apps Script отправляет письмо с 6-значным кодом (MailApp.sendEmail)
  3. При успехе — переключение на Шаг 2, фокус на `#otp1`, запуск resend cooldown (60 сек)
- Кнопка «← Назад» → `KipAuth.cancelLogin()` (закрыть экран входа, перейти в гостевой режим)

#### Шаг 2: ввод OTP (`#authStep2`)
- 6 отдельных input'ов `#otp1`...`#otp6` (`maxlength="1"`, `inputmode="numeric"`, `pattern="[0-9]"`)
- Авто-переход фокуса между полями при вводе (обработчик keyup в строке ~20 962)
- Вставка кода из буфера (autocomplete="one-time-code" на первом поле — iOS Safari подставляет SMS-код, Android — код из письма)
- Кнопка `#authVerifyBtn` → `KipAuth.verifyOTP()`:
  1. Склейка 6 цифр в строку, валидация `/^\d{6}$/`
  2. Запрос `api('verifyOTP', { email, code })` → Apps Script сверяет код с pending-записью
  3. При успехе — сервер возвращает `{ token, role, userId, email }`
  4. Клиент сохраняет token + кэш роли в localStorage
  5. Скрытие `#loginScreen`, запуск heartbeat, `_applyRoleToUI()`, переход на `dashboard`
- Кнопка «← Назад» → `KipAuth.backToStep1()` (очистка OTP-полей, возврат на Шаг 1)
- Ссылка «Отправить повторно» (`#authResendLink`) → `KipAuth.resendOTP()` (доступна после 60-секундного cooldown)
- Подсказка про папки «Спам» и «Промоакции» (Яндекс.Почта и Mail.ru часто туда кладут письма от Apps Script)

### Системная кнопка «← Назад» в верхнем углу экрана входа
`KipAuth.handleBackButton()` — контекстно-зависимое поведение:
- Если на Шаге 2 (OTP активен) → вернуться на Шаг 1 (`backToStep1`)
- Если на Шаге 1 (email) → `cancelLogin` (закрыть экран, гостевой режим)

### Heartbeat — продление сессии
- Запускается после успешного входа (`_startHeartbeat`)
- Интервал: 5 минут (`HEARTBEAT_INTERVAL`)
- Вызывает `api('heartbeat', { token })` — сервер продлевает `expiresAt` сессии
- При сетевой ошибке — **НЕ** разлогинивает (см. классификацию ниже)
- При `session_expired` / `no_session` — переходит в гостевой режим (НЕ показывает экран входа принудительно)

### Bootstrap стратегия (КРИТИЧНО — Task 33)

При загрузке страницы вызывается `KipAuth.bootstrap()`. Стратегия зависит от наличия token и кэша:

```
1. НЕТ ТОКЕНА:
   → ГОСТЕВОЙ РЕЖИМ (роль "Общий доступ", без heartbeat)
   → НЕ показываем экран входа принудительно

2. ЕСТЬ ТОКЕН + ЕСТЬ КЭШ РОЛИ в localStorage:
   → БЫСТРЫЙ ПУТЬ: мгновенно показать приложение с кэшированной ролью
   → Запустить heartbeat
   → В ФОНЕ запросить getCurrentUser для проверки сессии
     - Успех → обновить кэш (роль могла измениться на сервере)
     - session_expired/no_session → тихий переход в гостевой режим
     - Сетевая ошибка → оставить пользователя в приложении с кэшированной ролью

3. ЕСТЬ ТОКЕН, НО НЕТ КЭША (первый вход на этом устройстве):
   → МЕДЛЕННЫЙ ПУТЬ: ждём ответа сервера (старое поведение)
     - Успех → инициализация как обычно
     - session_expired/no_session → гостевой режим
     - Сетевая ошибка → показываем экран входа с текстом
       "Не удалось связаться с сервером. Проверьте подключение и обновите страницу."
       (токен НЕ удаляем, чтобы пользователь мог обновить страницу)
```

Это решает проблему «вылет при reload из-за временной ошибки сети».

### Классификация ошибок (КРИТИЧНО)

Все ошибки в `api()` помечаются `_kind`:
- `'NETWORK'` — `TypeError: Failed to fetch`, не-OK HTTP статус, HTML вместо JSON, таймаут, обрыв
- `'SERVER'` — корректный JSON с `data.ok === false`, например `session_expired`, `no_session`, бизнес-ошибка

**Правило:** NETWORK-ошибки **НЕ** сбрасывают токен и **НЕ** разлогинивают пользователя. Сервер продолжит попытки в heartbeat. SERVER-ошибки `session_expired`/`no_session` — реальный logout → гостевой режим.

### Retry для сетевых ошибок
`api()` делает 2 попытки с задержкой 1 сек **только** для NETWORK-ошибок. Серверные ошибки НЕ ретраятся (повторный запрос даст тот же результат).

### Что НЕ делать в системе auth
- ❌ Использовать `Content-Type: application/json` — сломает POST из-за CORS-preflight
- ❌ Сбрасывать токен при сетевой ошибке — пользователь потеряет сессию из-за временного сбоя сети
- ❌ Показывать экран входа принудительно после logout — пользователь переходит в гостевой режим (Task 38)
- ❌ Хранить пароли — система использует только OTP, паролей нет
- ❌ Сохранять OTP-коды на клиенте — код одноразовый, проверяется только на сервере
- ❌ Использовать один и тот же ключ localStorage с префиксом `kip8test:` для `kip8_session_token` — ключ должен быть общим с `kip8` для совместного входа

### Защита на уровне `_applyRoleToUI()`

При любой смене роли (или инициализации) вызывается `KipAuth._applyRoleToUI()`, который:

1. **Sidebar items** (`document.querySelectorAll('.sidebar-item')`):
   - Извлекает `page` из `onclick="navigateTo('xxx')"`
   - Сравнивает с `ROLE_ACCESS[role]`
   - Если нет доступа — `style.display = 'none'`

2. **Sidebar groups** (`document.querySelectorAll('.sidebar-group')`):
   - Если у группы есть атрибут `data-requires="library"` / `"kip-ios"` — скрывает ВСЮ группу целиком, если роли недоступна эта страница (включая внешние ссылки `<a>`, у которых нет `navigateTo`)
   - Иначе — скрывает группу, если все её `.sidebar-item` скрыты

3. **Dashboard menu buttons** (`.menu-btn`):
   - Аналогично sidebar items — извлекает `page` из `onclick`

4. **Секретные кнопки** (`#minesweeperBtn`, `#phonebookBtn`):
   - Скрыты, если роль не имеет доступа к `_SECRET_PAGES`

5. **Нижний бар** (`dashboardBottomBtn-docs`):
   - Скрывается для ролей без доступа к `docs` / `library` / `kip-ios` (т.е. для «Общий доступ» и «Запрет»)

6. **Кнопка «Выйти»** (`#sidebarLogoutBtn`):
   - Скрывается для гостевой роли «Общий доступ» (гостю не из чего выходить)

7. **Кнопка «Админ-панель»** (`#sidebarAdminBtn`):
   - Видна ТОЛЬКО роли «Админ»

### Защита на уровне `navigateTo()`

При попытке перейти на страницу без доступа — показывается экран «Нет доступа» (`#noAccessScreen`):
- Текст: «У вашей роли «<роль>» нет прав на раздел <page>»
- Кнопка «На главную» → `navigateTo('dashboard')`

### Защита админ-страниц (двойная)

В `KipAuth.canAccess()`:
```javascript
if (page === 'admin' || page === 'admin-users' ||
    page === 'admin-sessions' || page === 'admin-logs' ||
    page === 'admin-stats') {
    return this._cachedRole === 'Админ';
}
```
Даже если `ROLE_ACCESS` случайно включит admin-страницу в список, доступ всё равно разрешён только Админу.

### Кабельный журнал — просмотр и `canEdit`

Страницы кабельного журнала (`cable-journal-edit`, `cable-journal-add`, `cable-journal-view`) входят в `_KIP_IOS_PAGES` и доступны **всем ролям с доступом к КИП ИОС** для просмотра.

Право **записи** (добавления, правки, удаления записей) определяется **отдельно** столбцом «Добавить, править, удалить кабели» в «Карта ролей.xlsx» и управляется серверным флагом `canEdit`:
- **Чтение (просмотр)** — всем ролям с доступом к `_KIP_IOS_PAGES` (т.е. КИП ИОС и выше)
- **Запись** (`canEdit=true`) — только ролям: **Админ, ИТР ИОС, КИП ИОС pro**

Сервер возвращает `canEdit` в ответе `cableJournal.getColumns`. На клиенте:
- Если `canEdit=true` — показывается кнопка «+ Добавить»
- Если `canEdit=false` — кнопка скрыта, доступен только просмотр

Fallback на клиенте (`_computeCanEdit(editRoles)`) — на случай, если серверная версия `CableJournal.gs` старая и не вернула `canEdit`. Сравнивает `_cachedRole` с массивом `editRoles`.

## Ключевые архитектурные решения

### Service Worker (`sw.js`)
- `CACHE_VERSION = 'kipia-test-v404'` — инкрементируется при каждом обновлении
- `IMAGE_CACHE_VERSION = 'kipia-images-test-v3'` — отдельный кэш для картинок Google Drive, **переживает** обновления `CACHE_VERSION`
- `makeCacheKey()` — нормализует URL, отбрасывая query-параметры (для `?v=timestamp` cache-busting)
- App Shell pattern — навигационные запросы в офлайне отдают `index.html`
- **NetworkFirst для `data/*.json`** — всегда идём в сеть, cache-busting `?v=timestamp`, `cache: 'no-store'`
- **Stale-while-revalidate** для Google Drive картинок (через `IMAGE_CACHE_NAME`)
- **overscroll-behavior: contain** на `#page-devices` — отключение инерции прокрутки
- На `activate` удаляются все кэши кроме `CACHE_NAME` и `IMAGE_CACHE_NAME` — известная проблема SW-1/SW-2 (удаляет кэши других приложений на том же origin)

### Навигация — шевроны ‹‹
- Удалены все `nav-bar` (кнопки «Главная» + «Назад») со всех страниц
- Вместо них — два шеврона ‹‹ слева от заголовка в `page-inline-header`
- `chevronTap()`: 1 тап → `goBack()`, 2 тапа (300 мс) → `navigateTo('dashboard')`

### Изоляция localStorage
Префикс `kip8test:` для всех ключей, **КРОМЕ** сессионных (`kip8_session_token`, `kip8_cached_role`, `kip8_cached_email`, `kip8_cached_user_id`, `kip8_cj_cache_v1`, `kip8_cj_cols_v1`). Реализован через обёртку `isolateLocalStorage()` (строка ~9874 в `index.html`), переопределяющую `localStorage.getItem/setItem/removeItem`.

Сессионные ключи без префикса — для совместного входа между `kip8test` и `kip8` (если пользователь использует оба).

### datetime_to_serial() — конвертация Excel-дат в числовые значения

**Проблема:** Google Sheets может хранить число (например, `0.16`) с форматом ячейки «Time» или «Date». `openpyxl` возвращает тогда `datetime`/`time`/`date` объект вместо числа, что приводит к отображению «03:50:24» или «1900-03-03» вместо исходного значения в карточках.

**Решение (Task 77–78, v251+):** во всех `sync-*.py` добавлена функция `datetime_to_serial(val)`, которая конвертирует:
- `datetime` → Excel serial number (дни с 1899-12-30)
- `time` → дробная часть дня (секунды / 86400)
- `date` → Excel serial number

Применяется к колонкам из `NUMERIC_HEADERS_HINTS` (например: ID, № п/п, Kvy, DN, PN, Уставка, Длина, Год выпуска, № проекта, и т. д.). `convert-exam-tickets.py` также обновлён.

## 🔄 Архитектура синхронизации «клиент ↔ Apps Script ↔ Google Sheets»

Разделы **«Кабельный журнал»** и **«Расходомеры хозрасчётные»** реализуют двухуровневую архитектуру данных, отличающуюся от простых read-only разделов (приборы, клапаны и т.д.): данные не только читаются, но и **записываются** пользователем из приложения в Google Sheets через Apps Script.

Этот раздел описывает паттерн полностью — от серверного кода до клиентского UI — чтобы по нему можно было реализовывать новые разделы с двусторонней синхронизацией.

### Общая схема

```
┌──────────────┐     fetch (POST)      ┌────────────────────┐     SpreadsheetApp     ┌──────────────┐
│   Клиент     │ ──────────────────→   │   Apps Script      │ ──────────────────→   │ Google Sheets│
│ (index.html) │ ←──────────────────   │ (Code.gs + X.gs)   │ ←──────────────────   │              │
└──────────────┘     JSON ответ       └────────────────────┘     getValues()        └──────────────┘
       ↕                                    ↕
┌──────────────┐                    ┌────────────────────┐
│ data/*.json  │                    │ Utils.gs           │
│ (fallback)   │                    │ findSessionByToken │
│ localStorage │                    │ findUserById       │
│ (кэш)        │                    │ audit()            │
└──────────────┘                    └────────────────────┘
```

Три уровня данных на клиенте (по приоритету):
1. **`data/<section>.json`** — статический fallback, генерируется `sync-<section>.py` при деплое / CI
2. **`localStorage`** — кэш последнего успешного ответа сервера (переживает перезагрузку)
3. **API (`flowmeter.list` / `cableJournal.list`)** — свежие данные из Google Sheets через Apps Script

### Файловая структура паттерна

Для каждого раздела с двусторонней синхронизацией нужны файлы:

| Файл | Где | Назначение |
|------|-----|-----------|
| `X.gs` | Apps Script | Серверная логика: `list()`, `update*()`, `_requireRead()`, `_requireEdit()` |
| `Code.gs` | Apps Script | Маршрутизация: `action === 'x.list'` → `X.list(payload)` |
| `scripts/X.gs` | `kip8test/` | Справочная копия для Git (не деплоится автоматически) |
| `scripts/sync-x.py` | `kip8test/` | Python-скрипт: Google Sheets → `data/x.json` |
| `data/x.json` | `kip8test/` | Статический fallback для PWA (офлайн / до загрузки API) |
| `sw.js` → `ASSETS` | `kip8test/` | `data/x.json` добавляется в пред-кэширование |
| `index.html` → `XData` | `kip8test/` | Клиентский модуль: `_loadFallback()`, `load()`, `submitInput()` |

### Серверная часть (Apps Script)

#### Авторизация — _requireRead / _requireEdit

**⚠️ КРИТИЧЕСКИ ВАЖНО:** авторизация должна использовать **только реально существующие функции** из `Utils.gs`. Паттерн **обязан** совпадать с `CableJournal.gs`:

```javascript

_requireRead: function(token) {

    }
    return { user: user };
},

_requireEdit: function(token) {
    // Тот же паттерн, но с INPUT_ROLES + Utils.audit() при отказе
    if (!token) return { error: { ok: false, error: 'no_session' } };
    var session = Utils.findSessionByToken(token);
    if (!session) return { error: { ok: false, error: 'no_session' } };

    if (this.INPUT_ROLES.indexOf(user.role) === -1) {
        try { Utils.audit(user.email, 'X_ACCESS_DENIED', '', '', '...'); } catch (e) {}

```

**❌ ЗАПРЕЩЁННЫЕ функции (НЕ СУЩЕСТВУЮТ в Utils.gs):**

| Функция | Почему нельзя |
|---------|--------------|
| `Utils.verifyToken(token)` | Не существует. Вызывает `TypeError`. |
| `Utils.getCurrentUser({token})` | Это endpoint-обёртка, не внутренняя функция авторизации. |
| `Utils.logAction(...)` | Не существует. Использовать `Utils.audit(email, action, '', '', message)`. |

#### Методы возвращают `{ok, ...}` — без throw

Методы `list()` / `updateReading()` используют `_requireRead` / `_requireEdit` и возвращают объекты ошибок напрямую:

```javascript
list: function(payload) {

    if (auth.error) return auth.error;   // { ok: false, error: 'no_session' }
    var user = auth.user;
    // ... чтение данных ...
    return { ok: true, data: { meters: meters } };

```

Это гарантирует, что `Code.gs` не нужно менять при добавлении новых эндпоинтов — глобальный `catch` в `doPost` обработает непредвиденные ошибки, а бизнес-ошибки (no_session, access_denied) возвращаются как нормальные JSON-ответы.

#### Маршрутизация в Code.gs

Для каждого нового раздела добавить блок в `doPost()`:

```javascript
// --- <Название раздела> ---
else if (action === 'x.list') {
    return jsonResponse(X.list(payload));
}
else if (action === 'x.updateRow') {
    return jsonResponse(X.updateRow(payload));

```

**Payload** — единый объект `{ token, ...params }`. Клиент добавляет `token` автоматически через `_api()`, сервер извлекает `payload.token` в `_requireRead`/`_requireEdit`.

### Проблема локали дат (⚠️ Готча №1)

Google Sheets с **русской локалью** интерпретирует строковые даты неоднозначно:
- `"8/3/2026"` → Sheets парсит как **D/M/YYYY** = **3 августа** ← неправильно!
- Ожидается **M/D/YYYY** = **8 марта** (или наоборот, зависит от контекста)

**Решение:** записывать в Sheets **Date objects**, а не строки:

```javascript
// Запись (клиент → сервер):
_clientToDateObj: function(val) {
    // "8/3/2026" → new Date(2026, 7, 3) — Date object
    var m = String(val).match(/^(\d{1,2})\/(\d{1,2})\/(\d{4})$/);
    if (m) return new Date(+m[3], +m[1] - 1, +m[2]);
    return null;
},
sheet.getRange(row, col).setValue(dateObj);  // Date object, не строка!

// Чтение (сервер → клиент):
_sheetToClientDate: function(val) {
    if (val instanceof Date) {
        return (val.getMonth() + 1) + '/' + val.getDate() + '/' + val.getFullYear();
    }
    // fallback: DD.MM.YYYY → M/D/YYYY
},
```

Цикл: клиент `"8/3/2026"` → `_clientToDateObj()` → `Date(2026,7,3)` → `setValue()` → Sheets хранит Date → `getValues()` → `_sheetToClientDate()` → `"8/3/2026"` → UI `"03.08.2026"`.

### Content-Type: text/plain (⚠️ Готча №2)

Клиент отправляет POST с `Content-Type: text/plain;charset=utf-8`, **НЕ** `application/json`.

**Причина:** `application/json` — «non-simple» Content-Type, браузер отправляет CORS-preflight (OPTIONS). Apps Script **не определяет `doOptions`**, возвращает 405, браузер блокирует запрос.

`text/plain` — «simple» Content-Type, preflight не нужен, POST идёт сразу. Тело остаётся JSON-строкой, `Code.gs` парсит через `JSON.parse(e.postData.contents)`.

### Оптимистичное обновление UI

При вводе данных (например, показаний расходомера) клиент **сразу** обновляет UI, не дожидаясь ответа сервера:

```javascript
submitInput: function() {
    // 1. Оптимистичное обновление в памяти
    meter.prev = meter.curr;
    meter.curr = newValue;
    meter.datePrev = meter.dateCurr;
    meter.dateCurr = newDate;
    // 2. Перерендерить UI
    this.renderList();
    // 3. Отправить на сервер (в фоне)
    this._api('flowmeter.updateReading', { ... })
        .then(function() { KipToast.show('Показания сохранены'); self.load(); })
        .catch(function(err) { KipToast.show('Ошибка: ' + err.message); });
},
```

Если сервер вернёт ошибку — пользователь увидит тост, но UI уже обновлён. При следующей навигации `load()` перечитает данные с сервера и откатит оптимистичное изменение.

### Клиентский модуль — полная структура

На примере `FlowmeterData` (паттерн для новых разделов):

```javascript
var XData = {
    // --- Конфигурация ---
    _cacheKey: 'kip8_x_cache_v1',       // localStorage-ключ
    _loaded: false,                       // флаг: данные с сервера
    _canEdit: false,                      // право записи (клиентский чек)
    _EDIT_ROLES: ['Роль1', 'Админ'],      // роли с правом записи
    _DATA: [],                            // массив записей (пустой до загрузки)

    // --- API ---
    _api: function(action, payload) {
        var token = KipAuth.getToken();
        if (!token) return Promise.reject(new Error('Нет токена'));
        return KipAuth.api(action, Object.assign({ token: token }, payload || {}));
    },

    // --- Инициализация (3 уровня) ---
    init: function() {
        this.renderList();          // 1. Рендер текущего состояния (пустое при первой загрузке)
        this._loadFallback();       // 2. data/x.json → _DATA → renderList()
        this._restoreCache();       // 3. localStorage → _DATA → renderList()
        this.load();                // 4. API → _DATA → renderList() → _persistData()
    },

    // --- Fallback из data/x.json ---
    _loadFallback: function() {
        var self = this;
        fetch('data/x.json?v=' + Date.now(), { cache: 'no-store' })
            .then(function(r) { return r.ok ? r.json() : null; })
            .then(function(d) {
                if (d && Array.isArray(d.records) && d.records.length > 0) {
                    self._DATA = d.records;
                    self.renderList();
                }
            })
            .catch(function() {});
    },

    // --- Кэш localStorage ---
    _restoreCache: function() {
        var json = localStorage.getItem(this._cacheKey);
        if (json) {
            var cached = JSON.parse(json);
            if (cached && Array.isArray(cached.records)) {
                this._DATA = cached.records;
                this._loaded = true;
                this.renderList();
            }
        }
    },
    _persistData: function(records) {
        localStorage.setItem(this._cacheKey, JSON.stringify({ records: records, ts: Date.now() }));
    },

    // --- Загрузка с сервера ---
    load: function() {
        var self = this;
        var token = KipAuth.getToken();
        if (!token) return;
        this._api('x.list', {}).then(function(data) {
            if (data && Array.isArray(data.records)) {
                self._DATA = data.records;
                self._loaded = true;
                self._persistData(data.records);
                self.renderList();
            }
        }).catch(function(err) { console.error('x.list:', err); });
    },

    // --- Запись ---
    submitInput: function() { /* оптимистичный UI + _api('x.update', ...) */ },

    // --- Права ---
    _computeCanEdit: function() {
        var role = KipAuth._cachedRole;
        if (!role) return false;
        if (role === 'Админ') return true;
        return this._EDIT_ROLES.indexOf(role) !== -1;
    },
};
```

## 🔐 Автономная работа с GitHub (при наличии токена)

Если пользователь предоставил **GitHub Personal Access Token (PAT)** для репозитория `kip8test`, ИИ-ассистент работает **самостоятельно** — клонирует, правит, коммитит и пушит без участия пользователя. Раздел описывает обязательные правила такой работы.

### Условия активации режима

- Пользователь явно передал токен в чате (например: «вот токен: `github_pat_...`»).
- Токен имеет доступ к репо `bloknett-design/kip8test` (classic PAT `ghp_...` или fine-grained `github_pat_...` с правами `Contents: Read and write` на этот репозиторий).
- Пользователь не сказал «не коммить / не пушить» — если сказал, режим автономной записи **отключается**, правки выдаются только файлами в `/home/z/my-project/download/`.

### Безопасность токена (КРИТИЧНО)

1. **Токен хранится в файле `/home/z/.kip_pat`**. Не пишется в `worklog.md`, в коммиты, в комментарии кода, в `git config` (используется inline-форма `https://<USER>:<TOKEN>@github.com/...`).
2. **Не логировать токен.** В выводах `git remote -v`, `git push` и т. п. он может отображаться — не цитировать эти строки дословно в ответе пользователю и в `worklog.md`. Если нужно показать remote — заменить токен на `[REDACTED]`.
3. **Не пушить в основной репо `kip8`** без явного разрешения пользователя. Токен от `kip8test` ≠ токен от `kip8`.
4. После завершения задачи — **не сохранять** токен в проектных файлах. Следующая сессия должна получить токен заново от пользователя.

В `electron/main.js` реализован `autoUpdater` из `electron-updater`:

### Очистка кэша при запуске (Task 129, v2.1.7)

**Важно:** без этого механизма SW переживает обновление Electron-приложения и отдаёт закэшированный старый `index.html`.

В `electron/main.js` функция `cleanCacheOnStartup()` (ранее `cleanCacheOnVersionChange()`):
- **Всегда** очищает SW + cacheStorage при запуске (без проверки версии)
- Уровень 1 (до `createWindow()`): `session.clearCache()` + `session.clearStorageData({origin, storages: ['serviceworkers', 'cachestorage']})`
- Уровень 2 (после `dom-ready`, через JS API): `navigator.serviceWorker.getRegistrations() + unregister()`, `caches.keys() + caches.delete()`, перезагрузка с `?_nocache=ts`
- ~500 мс задержка при запуске
- После очистки Electron грузит свежий `index.html` с GitHub Pages

**Следствие:** для обновления `index.html` (CSS/JS) в десктопе **не нужна переустановка** — достаточно перезапустить приложение. Переустановка нужна только при изменениях в `electron/main.js` или `package.json`.

### Баг `isDesktop()` в Electron (Task 126)

**Симптом:** `window.matchMedia('(min-width: 1024px)').matches` в Electron иногда возвращает `false`, несмотря на окно 1280×800. Это ломает всю логику, завязанную на `isDesktop()` в `index.html`.

**Решение:** использовать CSS `@media (min-width: 1024px) + body:has(.page-content.active)` вместо JS-проверок. Применено в Task 126/127 для показа `#detailBreadcrumbBar` и `#flowDesktopTabs`.

### Баг `closeDetailPanel()` очищает крошки (Task 130)

**Симптом:** на странице списка расходомеров крошки оставались пустыми, хотя `detailBreadcrumbBar` показывался.

**Причина:** `navigateTo()` вызывал `if (isDesktop()) closeDetailPanel();`, а `closeDetailPanel()` очищал `bcContent.innerHTML = ''`. В Electron `isDesktop()=false` → `closeDetailPanel()` НЕ вызывался → `#detailBreadcrumbBar` оставался без `.active` класса → CSS `display: none` не сбрасывался.

**Решение Task 130:** убрать `if (isDesktop())` — `closeDetailPanel()` вызывается ВСЕГДА. Сразу после него для `flowmeter-data` восстанавливается `.active` класс и крошки.

## Принудительный десктопный режим в Electron (Task 131, v400)

**Проблема:** при уменьшении окна десктопного приложения ниже 1024px CSS media-запросы и `isDesktop()` переключали интерфейс в мобильный вид. Пользователь просил это убрать.

**Решение (только в `index.html`, десктоп переустанавливать НЕ нужно):**

В начале главного `<script>` (сразу после `<script>`, перед игрой «Сапёр») добавлен блок `ELECTRON: ПРИНУДИТЕЛЬНЫЙ ДЕСКТОПНЫЙ РЕЖИМ`:

1. **Определение Electron по User-Agent** — `var IS_ELECTRON = /Electron/i.test(navigator.userAgent)`. Флаг `window.__isElectron` из main.js ставится на dom-ready — ПОЗЖЕ выполнения скриптов страницы, поэтому для ранних проверок ненадёжен. UA-детекция синхронна и работает до первого рендера.
2. **Override `window.matchMedia`** — width-запросы вычисляются «как будто окно бесконечно широкое»: `(min-width: N)` → всегда `true`, `(max-width: N)` → всегда `false`, `(min-width: 768px) and (max-width: 1023px)` → `false`. Запросы без width-условий (`prefers-color-scheme`, `prefers-reduced-motion`) проходят к оригинальному matchMedia. Возвращается статичный аналог MediaQueryList (слушатели change — заглушки: перехода в мобильный режим больше нет). Благодаря этому `isDesktop()` всегда `true` в Electron — на корневом уровне решён баг Task 126 «isDesktop() возвращает false в Electron».
3. **Переписывание CSS media-условий** на лету (мутация `rule.media.mediaText`, рекурсивно, включая вложенные @media от Task 126):
   - `(min-width: 1024px)` → `all` (десктопные стили применяются всегда)
   - `(max-width: 1023px)` → `not all` (мобильные/планшетные стили не применяются никогда)
   - Fallback: если мутация не применилась (для Chromium нехарактерно), содержимое десктопных блоков добавляется отдельным `<style id="electronForceDesktopCss">` в конец `<head>`.
   - Мелкие брейкпоинты `(max-width: 400/480px)` и `(min-width: 481/520/600px)` не трогаются — они не влияют на переключение режимов и не срабатывают при minWidth окна 900.

**Проверено в headless Chromium (agent-browser):**
- Electron UA + окно 600px → десктоп (`isDesktop()=true`, top bar `flex`, `.app-header` скрыт, 21 media-блок переписан)
- Обычный браузер + окно 600px → мобильный (как раньше, регрессии нет)
- Обычный браузер + окно 1400px → десктоп (как раньше)

**Кому доступно:** фикс приходит через GitHub Pages при перезапуске десктоп-приложения (cleanCacheOnStartup из Task 129 сам подхватит свежий index.html). Переустановка Electron-приложения не требуется. Мобильная PWA и браузерная версия не затронуты.

**Синхронизация kip8test-desktop:** `index.html` синхронизирован (коммит `auto: sync index.html from kip8test@<hash>`), `electron/main.js` и `package.json` не менялись — новый релиз десктопа не нужен, версия остаётся `2.1.7`.

## Одинаковый размер кнопок на главной (Task 132, v401)

**Проблема:** закреплённые разделы на главной (`.pinned-items-row` в `#pinnedItemsContainer`) имели разную высоту — текст подписей переносился на разное число строк, нижние края рядов получались «ступенькой». Кнопка «Избранное» (`_fav`, KipFav) рендерится той же структурой `.pinned-item-cell > .pinned-item` — тоже выравнивается. Скрытые ролью ячейки (`display: none`) не участвуют в сетке. ### Актуализация Task 135 (v404) — центрирование прибора + 4 правки

Запрос пользователя: (1) во всех картинках приборы смещены вверх — центр сместить ниже, чтобы прибор был примерно в центре рамки; (2) отступы от рамки картинки до рамки строки — минимальные (2px); (3) при сортировке «Приборы по производствам» картинки убрать; (4) в мобильной версии картинки меньше, чтобы строки не расширялись.

**Анализ фото каталога** (скачаны превью, PIL-анализ bbox прибора): ВСЕ фото 512×512 (квадрат), прибор в верхней части кадра — центр прибора 34–42% высоты (в среднем ~36%), снизу ~35% пустое поле под подпись. Оптимум масштаба: k = 1/(2·0.36) ≈ 1.35–1.4.

**Реализация:**
1. **Структура:** миниатюра теперь обёртка `<div class="pb-section-title-thumb">` + `<img>` внутри (был голый img). Обёртка: 100×82, `overflow: hidden`.
2. **Центрирование прибора:** `img { height: 135%; object-fit: cover; object-position: center top }` — фото с запасом высоты прижато к верху, нижнее пустое поле уходит за низ рамки, прибор в центре (для прибора с центром 36% кадра — центр в рамке 39.8px при центре рамки 41px).
3. **Заглушки:** `img.thumb-ph { height: 100%; object-position: center }` — SVG-круг «КИП» без сдвига и обрезки. Класс ставится при рендере заглушки и в `onerror` (битое фото → заглушка с корректными стилями).
4. **Отступы 2px:** класс `with-thumb` на `.pb-section-title` при наличии картинки; CSS `.dev-group .pb-section-title.with-thumb { padding: 2px 36px 2px 2px }` (специфичность выше `.dev-group .pb-section-title` — иначе перебивается его `padding: 14px 16px`). Строка: 87px (82+2+2+1 бордер).

## Десктоп-релизы v2.1.0-v2.1.7 (Task 122-130)

### v2.1.0 (Task 122)

**Проблема:** после v2.0.0 в `kip8test-desktop` было ~27 коммитов (через sync-to-desktop), но `electron-updater` у клиентов не видел обновлений.

**Причина:** `build-desktop.yml` использует `--publish onTagOrDraft` — `latest.yml` публикуется ТОЛЬКО при пуше git-тега `v*`. После v2.0.0 ни одного нового тега не было создано.

**Решение:** bump `package.json` version 2.0.0 → 2.1.0 + push тег `v2.1.0`.

### v2.1.1 (Task 123)

**Проблема:** после установки v2.1.0 новый код не появился.

**Причина:** старый Service Worker пережил обновление Electron-приложения. SW и cacheStorage хранятся в `userData`, отдельно от кода Electron — обновление Electron-приложения их НЕ очищает.

**Решение:** `cleanCacheOnVersionChange()` в `electron/main.js` — при запуске сравнивает `app.getVersion()` с `userData/last-version.txt`, при несовпадении вызывает `session.clearCache() + clearStorageData({storages: ['serviceworkers', 'cachestorage']})`.

### v2.1.2 (Task 124)

**Проблема:** v2.1.1 не сработал — старый SW всё ещё отдавал закэшированный index.html.

**Причина:**
1. `session.clearStorageData()` без указания `origin` может не очистить SW для HTTPS origin
2. HTTP-кэш Chromium может отдать старый index.html через 304 Not Modified

**Решение:** двухуровневая очистка:
- Уровень 1 (до `createWindow()`): `session.clearCache()` + `clearStorageData({origin: 'https://bloknett-design.github.io', storages: [...]})` + `pendingDeepClean = true`
- Уровень 2 (после `dom-ready`): `executeJavaScript` → JS API `navigator.serviceWorker.getRegistrations() + unregister()`, `caches.keys() + caches.delete()`, `window.location.replace(url + '?_nocache=' + Date.now())`

### v2.1.3 (Task 125)

**Диагностическая сборка:** включён `devTools: true`, `autoHideMenuBar: false`, `openDevTools({mode:'detach'})` + через 3 сек после `dom-ready` — `dialog.showMessageBox` с диагностикой (URL, SW count/urls/controller, Cache Storage names, CACHE_VERSION, DOM-элементы Task 119/120, активная страница, viewport, UserAgent).

**Результат диагностики:**
- URL: `https://bloknett-design.github.io/kip8test/` ✓
- `#flowDesktopTabs: true` ✓ (элемент в DOM есть)
- `#flowFavBtn: true` ✓
- Cache Storage: `["kipia-test-v395", "kipia-images-test-v3"]` ✓
- SW controller активен

Вывод: HTML свежий, SW работает, элементы в DOM есть — но `#flowDesktopTabs` скрыт через inline `style="display:none;"` + JS не сбрасывал его (баг `isDesktop()`).

### v2.1.4 (Task 126)

**Проблема:** переключатель «Все / Избранные» не виден, хотя элемент в DOM есть.

**Корневая причина:**
- HTML: `<div id="flowDesktopTabs" style="display:none;">` — inline-стиль
- JS в `navigateTo('flowmeter-data')` сбрасывал inline display только если `isDesktop()` возвращал true
- `isDesktop() = window.matchMedia('(min-width: 1024px)').matches` — в Electron иногда возвращает `false`
- Звёздочки `.flow-card-fav-btn` видны, потому что CSS-правило `@media (min-width: 1024px) { display: none !important; }` для них ЗАКОММЕНТИРОВАНО в Task 119

**Решение:** CSS-only показ через `@media + :has()`:
```css
@media (min-width: 1024px) {
    body:has(#page-flowmeter-data.active) #detailBreadcrumbBar {
        display: flex !important;
    }
    body:has(#page-flowmeter-data.active) #page-flowmeter-data > .page-inline-header {
        display: none !important;
    }
}
```

### v2.1.5 (Task 127)

**Проблема:** «все кнопки в отдельной строке» — два header'а один под другим (`detailBreadcrumbBar` + `page-inline-header`).

**Решение:**

- Скрыть кнопки `✕` (close) и `⇄` (swap) когда `#detailPanel` НЕ активен

### v2.1.6 (Task 128)

**Проблема:** хлебные крошки не отображаются на странице списка расходомеров.

**Причина:** JS-код Task 120 заполнял `#detailBreadcrumbContent` только если `isDesktop()` возвращал true.

**Решение:** вынести заполнение крошек из `if (isDesktop())` блока — заполнять ВСЕГДА при заходе на `flowmeter-data`.

### v2.1.7 (Task 129) — последний релиз с переустановкой

**Контекст:** пользователь спросил, почему для обновления десктопа каждый раз нужна переустановка. Причина — `cleanCacheOnVersionChange()` очищал SW только при изменении версии Electron-приложения.

**Решение Task 129:** `cleanCacheOnStartup()` — ВСЕГДА очищает SW + cacheStorage при запуске (без проверки версии). После установки v2.1.7 переустановка больше не нужна для обновления `index.html`.

### Фикс кэша v399 (Task 130) — без релиза

**Решение Task 130:**

- `CACHE_VERSION` v398 → v399
